# Area: Architecture (`architecture`)

## Scope

How the site is put together, and whether that structure makes everyday changes slow, repetitive or risky. Think like the person who will maintain the site for the next three years: what happens when the header changes, when a new case study is added, when a new kind of page is needed, when a colour or button style changes?

Look at the **authored source**, not only at what is deployed. If pages are generated by a build from shared templates, duplication in the output is fine; if the source itself repeats the markup, it is not. When the source lives somewhere else (another branch, another repository, a CMS), find it (`git branch -a`, `git ls-tree <branch>`, `git show <branch>:<path>`) and say where it is.

Every problem here is an `issue` and counts towards the score. Most architecture problems are structural, so add `direction` (see the contract): the general approaches that would remove the cause, such as "shared layouts in a static site generator (Eleventy, Astro)" or "a component library with documented design tokens".

Answer these questions for every site, with evidence:

1. **Shared layout**: is the header, footer and navigation written once and reused, or copied into each page? Count the files that contain the same block (`structureClusters`, compare files, `git grep` a distinctive navigation string). Count how many files the last header or navigation change touched (`git log --stat`).
2. **Design system**: is there one place that defines colours, type, spacing and the reusable components (buttons, cards, sections), and is it documented so a new page can be built from it? Signals of its absence: hard-coded colours repeated across files, many unrelated class-name prefixes, `!important` overrides, the same component styled several ways, one ever-growing stylesheet.
3. **Content types**: which kinds of page exist (for example home, service, case study, blog post or insight, team, legal)? For each, is there a template and a defined set of fields, or is every page hand-built? Count the pages of each type.
4. **Source of truth**: is there exactly one place where content and code are edited? Two editable copies (source and committed output, two branches, a CMS and hand-edited files) mean fixes get lost.

## Out of scope

Rewrites for fashion: only report a structure when you can show the problem it causes in this project. The change process itself (branches, reviews, releases) belongs to the workflow area. Security and performance problems belong to those areas; mention them only as a consequence of a structural cause.

## Rules

| Rule | Default severity | What to check |
|---|---|---|
| `architecture.no-shared-layout` | high | Header, footer or navigation markup is copied into many authored files, so one change has to be repeated in each of them. Medium when fewer than 10 files. |
| `architecture.no-design-system` | medium | No single, documented set of design tokens (colours, type, spacing) and reusable components, so every new page is styled by hand and pages drift apart. |
| `architecture.no-content-model` | medium | Distinct content types (case studies, posts, team members, services) are hand-built pages instead of entries rendered through one template per type, so adding one means copying and editing a whole page. |
| `architecture.two-sources-of-truth` | high | Content or code can be edited in two places (source and committed build output, two long-lived branches, CMS and files), so fixes made in one are lost or must be repeated in the other. |
| `architecture.hand-edited-content` | medium | Content that changes often (people, prices, case-study teasers, articles) is written into markup in several places, so one change touches many files (`git.recurringChangeSets`, `git.subjectClusters`). |
| `architecture.no-build-pipeline` | medium | There is no build step, so assets cannot be optimised, checked or versioned automatically. |
| `architecture.framework-mismatch` | medium | The framework does not fit the site: a client-rendered app for a mostly static site, or a heavy framework for a few pages. |
| `architecture.monolithic-theme` | medium | Business logic lives in templates or a page builder, so changing content or layout risks breaking behaviour. |
| `architecture.legacy-frontend` | medium | Global scripts, jQuery-era patterns or no modules make changes risky and slow. |
| `architecture.legacy-leftovers` | low | Pages or assets from an earlier version of the site are still served outside the current structure (their own navigation, styles or scripts). |
| `architecture.mixed-concerns` | medium | Data access, business rules and presentation are mixed in the same files. |
| `architecture.i18n-by-copy` | medium | Languages are handled by copying whole pages, so every change has to be repeated per language. |
| `architecture.no-form-backend` | low | Forms post to `mailto:` or nowhere, so submissions are lost or never tracked. |

## Facts to record

- `architecture.framework`: framework or "none", and version.
- `architecture.rendering`: static, server-rendered, client-rendered or mixed.
- `architecture.contentSource`: where content is authored (markup, Markdown, CMS, database) and, if not on the main branch, where it lives.
- `architecture.contentTypes`: the kinds of page and how many of each, for example `{ "case-study": 17, "insight": 18, "service": 9 }`.
- `architecture.sharedLayout`: how the header, footer and navigation are shared (template, include, build step, copied).
- `architecture.designSystem`: where styles and components are defined, and whether they are documented.
